# Milestone 2 — InvoiceFlow Adoption Map

Starting HEAD: `951cd76`. InvoiceFlow reference HEAD: `0d08944` (read-only, `/Users/KWADW/Ai-Lab/agent-os/invoiceflow`, branch `main`).

This document records, pattern by pattern, what the CMS adopts closely from InvoiceFlow, what it adapts, what it preserves unchanged, and what does not apply — plus the two concrete defects the inspection phase confirmed in the CMS's current shell/theme code. It is the reference for this milestone's implementation and for any future milestone touching the shell.

## Inspection summary

**InvoiceFlow** (Next 16 / React 19 / Tailwind v4, CSS-first `@theme inline`, Radix + CVA + tailwind-merge "shadcn" pattern, Geist font via the `geist` package): a flat, restrained SaaS visual language — no glassmorphism, no gradients, no scale/glow micro-interactions. Semantic tokens (`--color-page`, `--color-surface`, `--color-surface-elevated`, `--color-text`/`-secondary`/`-muted`, `--color-border`/`-subtle`, `--color-accent`, semantic status colors each with a `-soft` background), a 3-tier radius scale (sm/md/lg, all ≤10px), a single popover shadow token, a named typography scale implemented as `.text-*` utility classes, and a shell built from `AppShell` (fixed 240px `hidden lg:flex` sidebar + sticky top bar with a mobile `Sheet`) plus a small set of Radix-based primitives (button, card, badge, input, select, dropdown-menu, tabs, tooltip, separator, label, skeleton).

**CMS current state** (Next 16 / React 19, same Tailwind v4 CSS-first setup, but no Radix beyond `react-slot`): an "Apple/macOS glassmorphism" system — HSL shadcn-style tokens, heavy `backdrop-blur`, gradients, hover-scale/glow effects, pill-shaped buttons, 24px card radii. `Sidebar.tsx`/`Header.tsx`/`MobileBottomNav.tsx` are substantial hand-built client components with real functionality (centre switcher, notifications, search, theme toggle) that must be preserved. Two confirmed shell defects, detailed below.

## Confirmed defects (inspection phase)

**Tablet overlap (breakpoint mismatch, three-way).** `Sidebar.tsx` switches from off-canvas to a fixed rail at `md:` (768px) and its mobile-close logic checks `window.innerWidth < 768`. `Header.tsx` offsets its left edge at `md:left-20`/`md:left-64` (768px). `DashboardContent.tsx`, however, only applies the matching `lg:ml-20`/`lg:ml-64` content margin at `lg:` (1024px), and `MobileBottomNav.tsx` only hides at `lg:hidden` (1024px). Between 768px and 1024px (e.g. 834px/iPad) the sidebar rail is visible and the header is offset, but the main content has no left margin (so content sits under the rail) **and** the bottom nav is still shown alongside the desktop rail. Fix: collapse the whole shell transition onto a single breakpoint (`lg`, 1024px — matching InvoiceFlow's own `hidden lg:flex` convention), so under 1024px the shell is unambiguously "mobile" (off-canvas sidebar + bottom nav) and at/above 1024px it is unambiguously "desktop" (fixed rail + margin, no bottom nav).

**Mobile theme flash (Tailwind dark-variant strategy, not a timing bug).** The CMS's actual theme state is class-based: `Header.tsx` toggles `document.documentElement.classList` between `dark`/`light`, and the root-layout inline script sets the same class before first paint from `localStorage`. But `globals.css` never declares `@custom-variant dark (&:where(.dark, .dark *));`, so Tailwind v4's `dark:` variant falls back to its default **media-query** strategy (`prefers-color-scheme: dark`) — completely independent of the app's own `.dark`/`.light` class. Nine-plus dashboard components use literal `bg-white dark:bg-slate-900` (and siblings) including `DashboardHero.tsx`'s sticky title bar — the element that sits directly behind the "Dashboard" heading. When the app's stored theme is dark but the device's OS-level colour-scheme preference is light (the common default on many phones), that bar renders `bg-white` regardless, producing a stark light bar behind the title in an otherwise dark UI — read by a user as a "flash" on first load. Fix: add the missing `@custom-variant` so `dark:` becomes class-based like the rest of the app already assumes. One-line root cause, app-wide correctness fix, no theme redevelopment.

## Adoption table

| Pattern | Decision | Notes |
|---|---|---|
| App shell (sidebar + top bar + content column) | **ADAPT** | Adopt InvoiceFlow's single-breakpoint (`lg`) mobile/desktop split and sticky-blur top bar composition; keep the CMS's existing functional sidebar (centre switcher, role-based nav, collapse toggle) and header (search, notifications, theme toggle) rather than replacing with InvoiceFlow's simpler nav-only shell. |
| Sidebar visual style | **ADAPT** | Flatten from glassmorphism/pill-nav to InvoiceFlow's flat surface + subtle active-state left rule; keep collapse-to-rail behaviour (InvoiceFlow has no collapse mode — CMS-specific, preserved) and the centre-selector dropdown and nested sub-items (Recovery Bin, Session Ledger), restyled onto the new tokens. |
| Nav item styling | **ADAPT** | InvoiceFlow's flat active/hover states (no scale/glow/pill), applied to the existing flat `navItems` + `children` structure. |
| Header / top bar | **ADAPT** | Keep search, notifications, theme toggle, user menu (all real functionality); restyle to InvoiceFlow's flat sticky-blur bar, align breakpoint to `lg`, and normalise its dropdown panels onto the new Radix `DropdownMenu` primitive instead of hand-rolled outside-click state where practical. |
| Mobile nav | **ADAPT** | Keep the CMS's own bottom-tab-bar pattern (InvoiceFlow uses a slide-in Sheet, not a tab bar — CMS's tab bar is a reasonable, already-mobile-idiomatic pattern for a small role-scoped nav; not blindly replaced) but fix its breakpoint to match the sidebar exactly. |
| Navigation grouping | **NOT APPLICABLE this milestone** | InvoiceFlow itself explicitly defers nav grouping (`nav-items.ts` comment) until warranted; the CMS's current flat 14-item list with two nested sub-items is not yet dense enough to need grouping, and regrouping is exactly the kind of route/IA change the ticket asks to avoid unless it earns its keep. Documented here so a later milestone can revisit once/if the nav grows. |
| Design tokens (colour, radius, spacing, shadow) | **ADOPT CLOSELY** | New semantic tokens added to `globals.css` mirroring InvoiceFlow's page/surface/surface-elevated, text tiers, border/-subtle, accent, semantic status (+ soft variants), 3-tier radius, single popover shadow. Added alongside (not replacing) the existing HSL/glassmorphism tokens so unmigrated operational-module pages keep rendering correctly; shell, primitives, and Dashboard consume the new tokens exclusively. |
| Typography scale | **ADOPT CLOSELY** | InvoiceFlow's named `.text-*` roles (page title, section title, card heading, body, small body, metadata, label) added as utility classes; applied in shell + Dashboard. |
| Buttons | **ADAPT** | CMS's `Button.tsx` is already CVA + Radix Slot, structurally identical to InvoiceFlow's — kept, restyled from pill/uppercase to InvoiceFlow's flat rectangular (rounded-sm) sentence-case treatment on the new tokens; variants/sizes preserved so all existing call sites keep working. |
| Inputs | **ADAPT** | New shared `Input` restyled on the new tokens; existing form fields migrate opportunistically only where shell/Dashboard touch them. |
| Selects / Dropdowns | **ADOPT CLOSELY (new primitive)** | CMS has no Radix `Select`/`DropdownMenu` today; add `@radix-ui/react-dropdown-menu`, `@radix-ui/react-select`, `@radix-ui/react-tooltip`, `@radix-ui/react-separator`, `@radix-ui/react-label` (dependency additions only, no business logic) and port InvoiceFlow's primitives near-verbatim, restyled onto CMS tokens. |
| Cards / Surfaces | **ADAPT** | New `Card`/`CardContent` primitive modelled on InvoiceFlow's (flat, `border` + `bg-surface`, no gradient/blur/scale); used in Dashboard KPIs and available for future migration. Existing `.glass-card`/`.kpi-card` utility classes untouched for other pages. |
| Badges | **ADAPT** | Existing `Badge.tsx` (CVA) restyled onto the new semantic-soft tokens; variant names preserved. |
| Empty states | **ADAPT** | Existing `EmptyState.tsx` restyled onto new tokens/radius; API unchanged. |
| Skeletons | **ADOPT CLOSELY** | InvoiceFlow's minimal `animate-pulse` skeleton primitive added for shell/Dashboard loading states alongside the CMS's existing shimmer skeletons (not replacing them everywhere). |
| Page container / page header / section header | **ADOPT CLOSELY (new primitives)** | New `PageContainer`, `PageHeader`, `SectionHeader` components introduced (CMS has no equivalent); Dashboard is the first consumer. |
| Centre context / switcher | **ADAPT** | InvoiceFlow's `business-switcher.tsx` dropdown pattern (Radix `DropdownMenu`, avatar-style glyph, name + role) is the visual model for the CMS's centre selector; `CentreFilterContext.tsx`'s business logic (cookie/localStorage persistence, `useCentreFilter`) is untouched — only the trigger/menu markup in `Sidebar.tsx` is restyled. |
| Dashboard composition | **ADAPT** | KPI cards restyled on the new `Card` primitive (flat, icon chip, value, label — InvoiceFlow's `financial-summary-widgets.tsx` grid is the model); hero/greeting simplified into `PageHeader`; onboarding checklist, schedule, and activity feed keep their existing data/behaviour, restyled onto new tokens/spacing. No query or business-logic changes. |
| Responsive breakpoints | **ADOPT CLOSELY** | Single `lg` (1024px) shell breakpoint, matching InvoiceFlow, replacing the CMS's inconsistent `md`/`lg` mix (see defect above). |
| Theme (light/dark) architecture | **PRESERVE + targeted fix** | The CMS's own light/dark toggle (class + localStorage + inline anti-flash script) is out of scope to redevelop; only the missing `@custom-variant dark` wiring is added so existing `dark:` usages actually respect it (see defect above). InvoiceFlow has no user-facing theme toggle at all, so there is nothing of its to adopt here beyond correctness. |
| Fonts | **PRESERVE** | CMS keeps `next/font/google` Inter (already configured, no network fetch needed at runtime); InvoiceFlow's move to the `geist` package (Geist Sans/Mono) is a brand identity decision out of scope for this milestone. |
| Operational modules (Students, Parents, Staff, Bookings, Attendance, Registrations, Incidents, Finance, Communications, Reports, Settings, Kiosk, Parent Portal, public booking/registration) | **OUT OF SCOPE** | Not redesigned; inherit only the new base tokens, typography, and shared primitives incidentally through the shell and any primitive they already import (e.g. `Button`, `Badge`). |
